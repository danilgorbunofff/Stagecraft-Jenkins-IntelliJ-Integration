## Goal

A log panel that opens huge Jenkins consoles instantly, scrolls to the **first error**, and tails running builds live — without ever loading a 500 MB log into memory.

## Deliverables

1. **`LogEditorPanel`**: a real read-only `Editor` from `EditorFactory` (never hand-rolled text widget — search/selection/folding/accessibility are free). Error gutter stripes via `RangeHighlighter`.
2. **Filter box over the log**: `error`, `warn`, `own-package-only` (a real log is ~90% framework noise), and a whitespace-collapse toggle.
3. **Scroll to the first error, not the end.** `Finished: FAILURE` is never useful; Declarative prints the failure *after* `End of Pipeline`, outside every stage — so search the whole log.
4. **Head-plus-window fetching** with the cap and the honest truncation message.
5. **`logText/progressiveText` live tailing** for a running build.

## Streaming architecture (§9.7 — the load-bearing part)

- **Never hold a whole large log in memory.** Neither console endpoint takes a byte range, and the error is usually at the **end**. So: **stream `/consoleText` once**, scanning as it arrives; spool to a temp file; record line-start offsets and the first error line on the way; keep **first 20 MB + rolling tail buffer (default 2 MB)**; drop the middle. The end of a 180 MB log is always on screen.
- **Never** build a `List<String>` of every line. Use an `IntArrayList` of line-start offsets into one `CharSequence`, or write to a temp file and open a read-only `VirtualFile` (required for the 50 MB case).
- Truncation must be **visible**: *"showing the first 20 MB and the last 2 MB of 180 MB — open in Jenkins"*. Silent truncation generates bug reports.
- Tail with `progressiveText` and only the delta — never re-fetch.

## progressiveText protocol (§9.5, verified by re-checks R1)

```
GET {build}/logText/progressiveText?start={offset}
  body             bytes from that offset onward
  X-Text-Size      the new offset to send next  (OPAQUE CURSOR — never compute from body)
  X-More-Data      true while running; ABSENT on a finished build (not "false")
```

- Poll every **2 s** while running; append only the delta; stop when `X-More-Data` is absent, or when the tool window closes / project is disposed.
- **`X-Text-Size` is an offset into Jenkins' raw log file** (hidden console annotations), not the byte length received: Day-0 recorded `X-Text-Size: 12263` vs `Content-Length: 12336` for ~2.9 KB of text. Never compute the next offset from the body.
- CRLF counts: `X-Text-Size` counts the CRLF pairs (R1: 5,029-byte body → `X-Text-Size: 5008`).
- `start` past the end resets to 0 and re-sends the whole log (R1) — tolerate, don't crash.
- R1 evidence says a **mid-log tail fetch works on a finished build** (`r1-finished.mid-log.headers.txt`); wire the cheap `progressiveText?start={size - N}` tail-fetch and record the outcome for R1.
- **Never use `progressiveHtml`** — Stagecraft must produce its own linkified view (9.6), resolving to source files, not Jenkins URLs.

## Perf budgets (§9.7)

| Budget | Target |
|---|---|
| Open the failed stage of the newest build | < 3 s on a 1,000-job server |
| Render a 50 MB console | must NOT load 50 MB into memory |
| IDE heap added by an open log | < 50 MB |

## Exit criteria

> A 50 MB generated log opens in under 3 seconds without exhausting the IDE heap, and a running build's log grows in the panel.

## What was built

**Headless (no IDE imports, all tested)**

- `ConsoleLog` / `ConsoleLogReader` — streams `/consoleText` or `progressiveText` **once**, tracking
  line numbers, the total count and the first error on the way, keeping the first 20 M characters in
  full and the last 2 M through a fixed-size `CharRing`, and dropping the middle. A `NoteStripper`
  removes console notes incrementally so the same reader serves both endpoints; a truncation banner
  is always produced, never silent. `CharRing` makes the rolling tail O(1) per character.
- `ConsoleTailer` — follows a running build with `logText/progressiveText`, appending only the delta
  and treating `X-Text-Size` as the opaque cursor. A cursor that goes backwards is surfaced as a
  reset (R1) rather than appended as a duplicate; `X-More-Data` absent means finished.
- `LogFilter` — `ALL` / `ERRORS` / `WARNINGS` / `OWN_PACKAGE` plus blank-line collapse. The error
  predicate is `ConsoleStages.isErrorLine`, shared with the parser so the two never drift.
- `JenkinsClient.withProgressiveText` / `withConsoleText` — stream the body as a `Reader` with the
  cursor read first, so a large log is never buffered.

**IDE**

- `LogEditorPanel` — a real read-only `Editor` from `EditorFactory`, `RangeHighlighter` stripes on
  error/warning lines, a filter combo + whitespace toggle, a truncation banner, and scroll-to-first-
  error. Live tailing polls `JenkinsService.tailConsole` every 2 s and appends deltas on the EDT;
  `dispose` stops it. `BuildTreePanel` opens it (double-click or **Open log**), and
  `BuildsToolWindowFactory` adds it as a closable tool-window tab.

**Evidence (tests)**

- `ConsoleLogTest`: short log, no-error, CRLF/CR, no trailing newline, head+tail truncation with the
  marker, first error found in the dropped middle, error offset in the retained text, the 50 MB
  bounded-memory stream, and the Day-0 equality (`progressiveText` notes stripped + CRLF normalised
  == `/consoleText`, first error line 72).
- `ConsoleTailerTest`: cursor advance, empty delta, finished, backwards-cursor reset.
- `LogFilterTest`: each mode, own-package with no tokens, whitespace collapse, warning predicate.
- `JenkinsClientTest`: the console streams into a bounded reader with its first error.

## Second audit (2026-10-03)

The audit confirmed these defects with probes. All are fixed with regression tests (`LogViewTest`, `ConsoleLogTest`, `JenkinsHttpTest`):

- **Live tail broke the memory cap.** `fullText += delta` grew without bound, copied the whole text on every tick, and inserted unfiltered text into a filtered view (`ERROR: onenext line`). The panel now drives a headless `LogView`. It trims live output to whole lines under the same head/tail caps, filters only complete new lines (a half line waits for its newline), and does work proportional to the delta.
- **Shared tail cursors.** Tailers were keyed by build URL and restarted at 0 after a settings change or when a second tab on the build closed, which appended the whole log again. Each tab now owns a tail handle. A client rebuild continues the same cursor, and a tick whose previous request is still on the wire is skipped instead of queued.
- **The 50 MB budget was neither met nor tested.**
  - `NoteStripper` allocated about three objects per character; it now streams to a sink (0.8 s instead of 3.0 s).
  - The `…` in the truncation marker forced two-byte strings; the marker is ASCII now.
  - Undo was recorded for every `setText` on a 22 M-char document; it is disabled.
  - Both are tested.
- **Line numbers didn't match the view.** Cuts snap to line boundaries, and full-log line numbers map through the dropped middle and the filter (`LogView.documentLine`). The status no longer names a line that the view isn't showing.
- **Closing the tab within about 3 s threw `RejectedExecutionException`.** Every callback now checks `disposed`.
- **A literal `ESC[8mha:` swallowed the rest of the log.** A newline ends a would-be note, and a trailing partial preamble is kept as text.
- **Visibility was read off the EDT.** It is now read on the EDT.
